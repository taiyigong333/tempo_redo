# 训练前应当考虑的问题集合

根据本次TEMPO双服务器复现、训练中断、动作表示核查和部署材料整理形成。更新时间为2026-11-14。

使用时按任务选择适用项，在每项后记录结论、证据位置和待办。表中的“源码或配置已核对”指本次仓库快照核验，实时训练状态与正式模型效果需读取对应运行记录。问题清单用于实验设计、启动前检查和后续交接。

## 一、这次训练究竟要验证什么

- [ ] 目标是复现论文中的哪个方法、哪张表、哪个任务和哪项指标？
- [ ] 本次选择单独TEMPO，还是启用u_t潜变量及decoder的组合路线？对应论文实验与官方代码配置是什么？
- [ ] “复现”具体覆盖模型实现、训练配方、数据规模、机器人平台、相机输入和评测协议中的哪些部分？
- [ ] 哪些内容由用户明确指定，哪些属于本次实现选择？这些选择是否已记入实验方案？
- [ ] 成功标准如何衡量？训练loss、离线动作误差、在线成功率、动态任务反应时间分别如何评估？
- [ ] 与论文设置存在差异时，最终报告如何说明适用范围？

**本项目需要优先确认的方法选择**。当前配置启用64维u_t及decoder。论文将TEMPO+UVT单独列为组合实验，严格对齐具体表格结果时，需要将训练目标、方法配置和论文实验对应起来。官方核心源码一致性与完整实验设置对齐分别记录。[TEMPO论文](https://arxiv.org/html/2609.16864)

## 二、机器人动作的物理含义是否清楚

- [ ] 输出采用关节空间，还是末端位置与姿态空间？数据字段、采集程序和控制接口是否一致？
- [ ] 每维分别是什么，单位是什么？关节角采用弧度还是角度，夹爪采用米、毫米、归一化开度还是其他编码？
- [ ] 动作表示采用绝对目标、相对当前观测的偏移，还是相邻时刻增量？相对量的参考状态取哪个时间点？
- [ ] 夹爪是否与关节使用相同的相对化规则？开合方向、零点和有效范围是否核实？
- [ ] 训练标签、模型内部输出、decoder输出和部署接口输出分别处于什么空间？
- [ ] 控制器接收位置、速度还是力矩命令？模型动作与其频率、插值和执行方式如何对接？

本项目数据字段为 `joint_1`～`joint_6` 与 `gripper_width`，属于6个关节位置与夹爪开度。现有数据元信息未给出明确物理单位，单位仍需从采集与控制代码核对。

当前decoder学习policy归一化后的关节相对量与绝对夹爪开度。对于整段30步动作，前6维的共同参考为本次观测关节角 $q_t$。

$$
\Delta q_{t,k}=q^{\mathrm{target}}_{t+k}-q_t,\qquad k=0,\ldots,29
$$

部署完成反归一化后，前6维加回同一参考状态，得到绝对关节目标。

$$
\hat q^{\mathrm{target}}_{t+k}=q_t+\widehat{\Delta q}_{t,k}
$$

完整链路为 $u_t\rightarrow\text{decoder}\rightarrow\text{归一化动作}\rightarrow\text{反归一化}\rightarrow\text{关节绝对化}\rightarrow\text{机器人控制接口}$。调用底层 `sample_actions` 后，还需由对应策略输出变换完成后处理。

## 三、数据是否真的支持这个任务

- [ ] 数据覆盖哪些物体速度、方向、初始状态、光照、遮挡、成功与失败情形？是否覆盖目标部署场景？
- [ ] action代表操作者命令、机器人实际执行目标，还是事后记录的状态？各字段的来源和时间定义是什么？
- [ ] 图像、state、action是否按相同时间基准对齐？采集延迟、丢帧和动作执行延迟如何处理？
- [ ] episode边界、帧号、时间戳、视频帧数与Parquet记录是否一致？
- [ ] 是否检查NaN、Inf、异常跳变、重复轨迹、截断轨迹和夹爪异常值？
- [ ] 数据统计与内容校验能否对应到具体数据版本和文件指纹？

本项目已记录393轨迹、44398帧、786路轨迹视频、30Hz及两路224×224相机。历史校验显示 `action[t]` 与 `state[t+1]` 数值完全一致，需要结合采集代码解释这一关系，明确state代表测量反馈还是记录后的命令状态，并核对时间对齐。

## 四、划分、归一化和缓存是否配套

- [ ] 训练、验证、测试按什么单位划分？同一轨迹或同一采集场景是否跨集合泄漏？
- [ ] 采用全量训练时，独立评测数据从哪里取得？best模型按什么指标选择？
- [ ] 归一化统计在哪个集合拟合，拟合发生在绝对化还是相对化之后？
- [ ] MVAE、自监督目标、decoder与policy分别使用哪些统计？加载时如何对应？
- [ ] RGB、SAM2和u_t缓存是否与原始数据、动作窗口、预处理和辅助权重一一对应？
- [ ] 数据、窗口、辅助权重或预处理变化后，哪些缓存与统计需要重新生成？

当前正式配置为train393、val0，policy的 `eval_interval=0`，辅助模型按训练loss选择best。当前数据安排对应全量拟合，独立泛化表现需通过另外设计的评测获得。MVAE保存自身动作统计，decoder学习policy归一化空间，两者的统计来源应随检查点记录。

## 五、模型配置与输入输出是否对齐

- [ ] 基座、官方源码提交、权重转换方式、词表和Transformers补丁分别对应哪个版本？
- [ ] 每项模型开关会启用哪个分支，是否符合目标论文方法？
- [ ] action_dim、有效动作维度、latent_dim、flow位置数、action horizon与decoder窗口分别是多少？
- [ ] 改动窗口或动作维度后，时间位置参数和输入输出投影的权重形状是否兼容？
- [ ] 相机数量、名称、历史帧间隔、SAM2特征和动作历史的形状与时间语义是否匹配？
- [ ] 权重加载中的missing、unexpected及shape mismatch分别来自哪里？哪些层继承基座，哪些层按当前配置初始化？

本项目当前约定如下。

| 项目 | 当前配置 |
|---|---|
| 基座 | π0.5 |
| 模型动作接口 | 32维 |
| 机器人有效动作 | 7维 |
| u_t与flow维度 | 64维 |
| flow位置数 | 1 |
| action horizon与辅助窗口 | 30 |
| decoder有效输出 | `[B,30,7]` |
| 策略采样padding输出 | `[B,30,32]` |
| 图像历史 | 两路相机，各3帧 |
| SAM2特征 | 64个256维token |
| 动作历史 | 10个7维桶，每桶30帧 |

核心模型类按官方实现核对。任务配置实例的参数形状与推理资源仍需逐项核对，尤其是30帧/7维辅助权重与历史16帧/14维配置的对应关系。

## 六、辅助训练与标签来源是否可追溯

- [ ] MVAE、u_t编码、decoder、policy的依赖顺序是否清楚？每阶段输入输出各是什么？
- [ ] 辅助模型是否覆盖本次数据与动作窗口？复用权重的来源、配置、数据版本和统计是否齐全？
- [ ] u_t取哪种潜变量统计，维度与生成窗口如何定义？尾部缺少完整窗口时如何mask？
- [ ] decoder训练是否包含当前动作相对化和policy归一化规则？其 `action_space` 标记是否与实际处理一致？
- [ ] 测试用辅助权重、测试标签与正式产物能否从目录、manifest及 `test_only` 字段区分？

ma800曾复用前一实验完成的MVAE、u_t和decoder，来源记录在其正式配置 `restoration.reuse_auxiliary_from`。GPU-Server执行自身辅助阶段。比较两台服务器的policy结果时，需要同时核对辅助权重来源。

## 七、优化器、精度和有效batch是否按实际执行核对

- [ ] 实际调用哪个优化器，参数精度、梯度精度、动量精度及训练状态所在设备分别是什么？
- [ ] 学习率、warmup、衰减总步数、betas、eps、weight decay和clip值，是否由真实入口落实？
- [ ] 全局batch如何由world size、每卡样本数与梯度累积得到？不整除或占位样本如何加权？
- [ ] 改micro-batch后，采样顺序、梯度权重、随机数和浮点归约顺序有哪些变化？
- [ ] train/eval、图像增强、dropout与冻结参数集合是否符合目标配置？
- [ ] 随机种子、每rank随机状态、数据采样步数和恢复入口是否可追踪？

当前policy使用原生AdamW与BF16 autocast，global batch128。ma800为两卡micro32、累积2，GPU-Server为四卡micro32、累积1。学习率等部分参数由 `train.py` 写入实现，启动前应同时核对JSON、组装后的命令及入口源码。

## 八、加速是否同时满足正确性和显存预算

- [ ] 当前瓶颈在视频解码、数据读取、特征编码、计算、通信、检查点写盘还是上传？
- [ ] 加速候选是否在固定真实样本、随机状态下对照loss与梯度？允许怎样的数值误差？
- [ ] fused优化器、编译、重算开关或精度调整会怎样影响数值轨迹和权重格式？
- [ ] 是否测量完整更新、优化器step、保存和恢复阶段的峰值显存？
- [ ] 吞吐测量是否排除启动预热，并记录同卡共享负载及测量区间？
- [ ] OOM后如何回退micro-batch与累积，global batch和样本权重如何保持对应？

GPU-Server历史短测中，micro32完整策略峰值分配显存约61.80GiB/卡。关闭外层重算在batch1数值对照通过，在batch32两次OOM。该候选未进入正式配置。用户约80%显存目标适用于policy，辅助模块采用高吞吐方案。实际可用显存还需计入预留显存、CUDA上下文和共享任务。

## 九、检查点能否真正恢复训练

- [ ] 首个可恢复检查点多久产生？此前中断会损失多少计算？
- [ ] 模型、优化器、调度器或调度步数、逐rank随机状态、数据顺序、配置及统计是否保存齐全？
- [ ] 是否先完整写入临时目录，再发布latest指针？旧滚动版本何时清理？
- [ ] 是否用当前保存入口实际恢复，并验证下一次更新？验证用小模型还是完整策略？
- [ ] 恢复对world size、global batch、micro-batch和环境版本有哪些约束？
- [ ] 滚动快照、长期里程碑、磁盘空间、上传快照和失败缓存如何规划？

当前约定为每100步更新状态并保存滚动检查点，每1000步保留里程碑及发布。ma800保存逐rank完整AdamW状态，GPU-Server格式v2保存一份共享AdamW状态及逐rank随机状态，恢复入口要求匹配原world size。历史曾在618步中断时尚无首个千步检查点，已有训练进度因此无法恢复。

## 十、作业运行与故障处理符合用户要求吗

- [ ] GPU物理编号、CUDA可见编号与UUID是否核对？作业使用哪组卡？
- [ ] 开始训练的资源条件、运行后的资源争用处理和故障退出条件分别是什么？
- [ ] 断开SSH或关闭本地电脑后，训练、代理、日志和上传是否继续运行？
- [ ] loss非有限、进度停滞、进程退出、OOM和网络故障分别如何判定与处理？
- [ ] 失败后自动重试还是交由用户决策？当前控制器加载的是哪版配置？
- [ ] 配置改动是否需要重启，有无完整检查点可接续，原日志与故障记录如何保留？

当前资源约定允许显存足够时共享GPU，运行中记录外部任务。ma800失败后的决策由用户作出，其配置 `max_stage_attempts=1`，历史旧控制器另有恢复守护。GPU-Server配置为最多3次尝试。服务器巡检、tmux持久会话和聊天通知需分别核实实际部署状态。

- [ ] 权重上传是否同时提供匹配配置、norm、decoder、必要源码与使用说明？

本项目W&B分别使用 `tempo-piperx-ma800` 与 `tempo-piperx-gpu-server`。ma800辅助模型位于ModelScope数据集根目录 `ma800/`，其policy位于对应 `runs/` 实验路径。GPU-Server统一位于 `gpu/gpu_paper_chunk30_4gpu_20261114/`。

## 十三、本项目当前最值得补齐的结论

下表按已有证据列出待确认与待实测内容，便于下一轮实验设计时直接填写。

| 问题 | 当前证据 | 下一项需要记录的结论 |
|---|---|---|
| 论文方法与训练目标对应 | 当前启用u_t及decoder，论文单列TEMPO+UVT组合 | 本次目标对应哪条方法路线、哪张实验表 |
| 关节与夹爪单位 | 已核对字段名称，元信息未标单位 | 采集和控制程序中的物理单位及取值范围 |
| 动作与state时间关系 | 历史校验为 `action[t]=state[t+1]` | 字段的采集来源与时间对齐含义 |
| 全量训练后的泛化评测 | 当前train393、val0 | 独立评测场景、指标及试验次数 |
| 官方初始化的分支学习行为 | SAM2采用官方双零初始化，历史出现gate梯度0 | 后续训练中该分支参数和梯度的实际变化及其解释 |
| 部署端完整后处理 | 源码已核对DeltaActions与AbsoluteActions | 正式服务入口加载权重后的完整动作链路验证 |
| 历史工具适配 | 部分独立工具引用已移除配置字段 | 实际准备使用的评测、对照脚本是否兼容当前入口 |
| GPU-Server保存恢复 | 已有完整策略step2保存并恢复至step3的短测报告 | 正式检查点的保存、恢复与发布记录 |
| ma800失败处理 | 配置限制一次尝试，历史有额外守护 | 新一次作业的控制器、配置和用户决策方式对应关系 |

本表的条目是后续核对入口，检查状态应随新证据更新。当前训练实时进度应从服务器状态与日志获取。
